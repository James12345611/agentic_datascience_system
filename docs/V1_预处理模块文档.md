# V1 预处理模块文档

## 1. 文档目标

本文档用于定义数据科学智能平台 V1 阶段“数据预处理模块”的目标、范围、当前实现状态、接口边界和后续演进方向。

这里的预处理模块不是孤立的清洗工具，而是整个统计分析与建模链路的入口层。它负责把原始结构化数据转成可用于统计检验、EDA、建模和看板展示的标准化数据资产。

## 2. 模块定位

预处理模块负责解决以下问题：

- 数据能否被系统正确读入
- 字段类型是否被正确识别
- 字段是否存在缺失、异常、重复或格式问题
- 是否需要人工补充单位、范围、比例、语义等元数据
- 数据是否已经具备进入后续分析与建模的条件

V1 的原则是：

- 规则和算法负责执行
- 人工负责纠偏与确认
- agent 负责辅助建议，而不是直接隐式改数据

## 3. 当前实现状态

截至当前版本，V1 已经完成的能力包括：

- CSV / Excel 上传
- 原始数据落库到 `raw_dataset`
- 字段类型自动识别
- 中文字段字典展示与人工修订
- 语义类型、单位、软范围、备注持久化
- 预处理执行并落库到 `preprocessed_data`
- 预处理任务日志记录
- 原始数据 / 预处理数据预览
- React 工作台调用真实 FastAPI 接口执行预处理

当前仍然偏“字段级规则 + 任务级执行”的形态，还没有做到完全细粒度的列级策略编排。

## 4. V1 范围

### 包含内容

- 结构化表格数据读入
- 数据预览
- 字段类型识别
- 字段字典人工修订
- 基础数据质量检查
- 基础清洗
- 编码与缩放
- 时间字段拆解
- 预处理结果持久化
- 任务日志与监控

### 暂不包含

- 深度自动特征工程
- 超大规模分布式数据处理
- 图像、文本、音频等多模态预处理
- 强化学习相关数据流
- 完整的可视化流程编排器

## 5. 支持的数据类型

V1 优先支持结构化数据中的以下类型：

- 数值型
- 分类型
- 时间型
- 布尔型
- 文本型
- 标识型

其中“识别类型”和“语义类型”是两层概念：

- 识别类型：字段在程序里的基础数据类型
- 语义类型：字段在业务中的含义，例如比例、金额、地理区域、行政区划等

## 6. 字段字典设计

### 为什么需要字段字典

单靠自动识别无法可靠判断以下信息：

- 百分比还是普通数值
- 金额还是计数
- 城市群名称是普通分类还是地理区域
- 时间字段是年、月、日还是更复杂的时间索引
- 单位是否存在量纲约束
- 字段是否有合理取值范围

因此 V1 中字段字典是预处理模块的关键配置层。

### 当前字段字典可维护信息

- 字段名
- 数据类型
- 语义类型
- 单位
- 软范围
- 备注

### 当前语义类型示例

- 普通字段
- 比例
- 金额
- 计数
- 评分
- 指数
- 时长
- 普通分类
- 有序分类
- 地理区域
- 行业分类
- 行政区域
- 时间索引
- 布尔标签
- 文本标签
- 自定义

### 设计原则

- 分类、文本、标识类字段默认不开放数值量纲配置
- 时间字段允许维护专属时间属性
- 数值字段支持单位、范围、比例等约束
- 所有人工修订都应持久化并可追溯

## 7. 当前预处理能力

## 7.1 数据读入

支持：

- `csv`
- `xlsx`

输出：

- 原始 `DataFrame`
- 数据集元信息
- 预览结果

## 7.2 字段类型识别

当前可识别：

- `numerical`
- `categorical`
- `datetime`
- `boolean`
- `text`
- `id_like`

同时会输出人工复核建议，供前端字典页修订。

## 7.3 数据质量检查

当前会检查：

- 样本量与字段量
- 缺失值比例
- 唯一值比例
- 重复记录
- 数值分布摘要
- 类别分布
- 时间解析结果
- 类型可疑字段

## 7.4 基础清洗

当前支持：

- 删除重复行
- 删除全空列
- 删除单一值列
- 删除指定列
- 缺失值填充
- 基础异常值处理

### 当前缺失值策略

- 数值型：均值 / 中位数 / 固定值 / 不处理
- 分类型：众数 / 固定值 / 不处理

### 当前异常值策略

- 不处理
- IQR 截断
- 分位数截断
- IQR 删除异常样本

## 7.5 编码与缩放

当前支持：

- One-Hot 编码
- 标签编码
- 标准化
- Min-Max 归一化

## 7.6 时间字段处理

当前支持：

- 自动识别时间字段
- 将年份、年月类字段解析成时间
- 拆解出年、月、日、季度、星期等衍生字段

## 7.7 结果持久化

当前结果会保存到：

- `raw_dataset`
- `preprocessed_data`
- `task_run`
- `task_step_log`
- `dataset_dictionary_override`
- `dataset_dictionary_revision`

## 8. 接口边界

当前与预处理强相关的接口包括：

- `POST /api/datasets/upload`
- `GET /api/datasets`
- `GET /api/datasets/{dataset_id}/preview`
- `GET /api/datasets/{dataset_id}/dictionary`
- `PATCH /api/datasets/{dataset_id}/dictionary`
- `POST /api/preprocess/run`
- `GET /api/tasks/{task_id}`
- `GET /api/tasks/{task_id}/logs`
- `GET /api/tasks/{task_id}/monitoring`

这意味着 V1 的预处理模块已经完成了从“本地函数”到“接口化能力”的过渡。

## 9. Agent 在 V1 中的角色

V1 中 agent 只做建议层，不直接改数据。

### Data Profiling Agent

输入：

- 数据概览
- 字段类型识别结果
- 质量检查结果

输出：

- 数据结构总结
- 风险字段提示
- 可疑类型说明

### Preprocess Planner Agent

输入：

- 字段字典
- 质量报告
- 分析目标描述

输出：

- 预处理策略建议
- 建议删除字段
- 缺失值处理建议
- 编码与缩放建议
- 潜在数据泄漏提示

### 为什么不把处理逻辑直接做成 skill 交给 agent 决策

原因不是不能做，而是 V1 阶段更应优先保证：

- 处理逻辑确定
- 可重复执行
- 参数可追踪
- 结果可复现

也就是说，当前更适合“agent 提建议，规则管执行”的模式。等后续规则体系和元数据体系更稳定，再考虑把某些策略选择抽象成 skill。

## 10. 当前限制

目前仍有以下边界：

- 缺失值与异常值策略还不够细到每列独立编排
- 量纲、单位、范围更多依赖人工修订
- 复杂业务校验规则尚未模块化沉淀
- 暂不支持 Spark / Databricks 等大数据处理引擎
- 任务执行仍以同步为主，后续应异步化

## 11. 下一步建议

预处理模块的下一阶段应重点推进：

- 列级预处理策略配置
- 单位、范围、比例、量纲的验证规则化
- 时间字段专属元数据配置
- 更丰富的数据质量告警
- 预处理方案模板化
- 与建模模块共享统一字段元数据
- 与任务中心打通重跑和版本对比

## 12. 一句话结论

V1 预处理模块已经完成了“能上传、能识别、能人工纠偏、能执行、能落库、能在 React 工作台触发”的基础闭环。下一阶段的重点不是推翻重做，而是在现有框架上把字段级策略、元数据约束和任务可追溯能力继续做深。
