# 原型到产品化迁移路线图

## 1. 文档目的

这份文档用于回答一个现实问题：

当前项目已经有了 `Python + Streamlit + SQLite` 的原型基础，后续如果要逐步发布为正式产品，应该如何从现在的形态平稳演进到：

- `React 前端 + Python 后端`
- `PostgreSQL 业务数据库`
- `异步任务系统`
- `对象存储`
- `Nginx + Docker` 部署

这份路线图不追求一次性把所有技术栈都引入，而是强调：

- 先把核心能力做稳
- 再把能力接口化
- 最后再做正式前端和部署升级


## 2. 当前项目所处阶段

当前项目本质上仍然属于：

`产品原型验证阶段`

当前阶段已经具备的能力包括：

- 数据上传与读取
- SQLite 原始数据和预处理结果存储
- 字段类型识别
- 人工字段标注
- 数据质量报告
- EDA 可视化
- 统计检验
- 统计诊断
- 预处理流程执行

当前技术形态：

- 前端：`Streamlit`
- 核心逻辑：`Python`
- 数据库存储：`SQLite`
- 运行方式：本地单机

这套技术栈非常适合当前阶段，因为它能让我们快速验证：

- 功能是否正确
- 流程是否顺
- 数据结构是否合理
- 用户是否真的需要这些能力

但它不适合作为正式产品长期交付形态，因为会逐步遇到这些限制：

- 前端交互复杂度有限
- 页面状态管理能力有限
- 多角色、多用户、多任务并发支持弱
- 权限体系和产品级页面结构不够灵活
- 长耗时任务处理体验一般


## 3. 路线总原则

后续演进遵循四条原则：

### 3.1 先做能力内核，再做正式前端

对于数据科学产品，真正难的不是“页面能不能点”，而是：

- 数据处理逻辑是否正确
- 字段元数据体系是否稳定
- 统计检验和建模过程是否可追踪
- 结果结构是否统一

所以正式前端一定要建立在稳定的后端能力之上。

### 3.2 先接口化，再替换前端

在当前阶段，不需要立刻重写前端。

更合理的做法是先把现有能力抽象成接口：

- 输入结构是什么
- 输出结构是什么
- 哪些接口同步执行
- 哪些接口异步执行
- 结果如何持久化

这样未来 React 前端接入时，只需要调用 API，而不用重写算法逻辑。

### 3.3 先单机稳住，再分层部署

先在本地单机把：

- 数据流
- 任务流
- 存储结构
- 输出结果

全部跑通。等能力稳定后，再做：

- 前后端分离
- 任务队列
- 反向代理
- 容器化部署

### 3.4 让学习成本服务进度，而不是反过来

你当前最熟悉的是 Python。

所以合理策略不是现在同时去系统学习：

- React
- TypeScript
- ECharts
- PostgreSQL
- MinIO
- Nginx

而是：

- 当前只做“需要现在就会”的部分
- 对未来技术栈先理解角色和接入时机
- 等产品进入下一阶段时再逐步补齐


## 4. 推荐的阶段划分

建议将整个项目拆成 4 个阶段。


## 5. 阶段 A：原型能力做厚

### 5.1 阶段目标

继续基于当前 `Streamlit + Python` 原型，把核心分析链路做扎实。

### 5.2 这一阶段优先做什么

优先完成这些内容：

- 字段字典和字段语义体系继续完善
- 预处理流程细化
- 统计检验体系继续完善
- 统计诊断继续完善
- 建模模块的输入输出结构设计
- 结果对象统一格式
- 日志、报告、产物的结构化保存

### 5.3 这一阶段暂时不要做什么

不建议现在重投入做：

- 正式 React 前端
- 多用户权限系统
- Nginx 正式部署
- MinIO 对象存储
- 大而全的微服务拆分

### 5.4 这一阶段产出物

这一阶段完成后，应该至少沉淀出：

- 稳定的数据分析主链路
- 统一的字段元数据结构
- 统一的任务输入/输出结构
- 一套可复用的服务层函数


## 6. 阶段 B：后端接口化

### 6.1 阶段目标

把当前原型中的核心能力逐步抽成 API。

此时前端仍然可以继续用 Streamlit，但 Streamlit 不再直接深度耦合业务逻辑，而是逐步变成“接口消费者”。

### 6.2 推荐后端框架

推荐：

- `FastAPI`

原因：

- 你已经在 Python 技术栈里
- 非常适合做数据平台接口
- 文档自动生成能力强
- 和 Pydantic、异步任务体系兼容好

### 6.3 这一阶段要抽出来的接口

建议优先抽这些接口：

#### 数据接入类

- 上传原始数据
- 查询原始数据列表
- 获取原始数据详情

#### 字段与元数据类

- 获取字段识别结果
- 提交人工字段标注
- 保存字段字典
- 查询字段字典

#### 预处理类

- 创建预处理任务
- 查询预处理任务状态
- 获取预处理结果

#### EDA 类

- 获取基础画像
- 获取图表数据
- 获取统计检验结果
- 获取统计诊断结果

#### 建模类

- 创建建模任务
- 查询建模状态
- 获取模型结果

### 6.4 这一阶段的关键思想

这一阶段最重要的不是“接口多”，而是“接口边界清晰”。

每个接口都要明确：

- 输入参数结构
- 输出结果结构
- 是否立即返回
- 是否返回 `task_id`
- 结果落在哪张表


## 7. 阶段 C：异步任务系统

### 7.1 为什么要引入异步任务

当系统开始处理这些任务时，同步接口就不够用了：

- 大文件解析
- 大数据预处理
- 批量统计检验
- EDA 报告生成
- 机器学习训练
- 深度学习训练
- 超参数搜索
- 模型解释
- 报告导出
- Agent 长流程分析

这时就必须把“请求提交”和“任务执行”分开。

### 7.2 推荐技术

推荐：

- `Celery` 或 `RQ`
- `Redis` 作为队列中间件

### 7.3 推荐任务模式

前端或调用方发起任务时：

1. 提交任务请求
2. 后端立即返回 `task_id`
3. 前端轮询任务状态接口
4. 任务完成后再请求结果接口

### 7.4 当前最适合先异步化的模块

建议优先把这些功能变成异步任务：

- 预处理任务
- EDA 报告生成
- 统计检验批量执行
- 建模任务

### 7.5 当前阶段是否需要 WebSocket

不必一开始就上 WebSocket。

对于当前产品阶段，优先使用：

- `task_id + 轮询`

就足够了。

WebSocket 可以在后面任务量更大、交互更复杂时再补。


## 8. 阶段 D：正式产品前端

### 8.1 为什么不建议继续只用 Streamlit

当系统变成正式产品后，会出现这些需求：

- 更复杂的页面状态管理
- 多模块导航与工作台布局
- 更灵活的交互设计
- 权限与角色控制
- 多任务进度与任务中心
- 产品级图表与看板

这些都不适合继续完全依赖 Streamlit。

### 8.2 推荐正式前端技术栈

推荐：

- `React`
- `TypeScript`
- `Ant Design`
- `ECharts`

### 8.3 对你当前阶段的影响判断

你现在还不熟悉 React、TypeScript、ECharts，这不会阻碍当前主线。

因为当前主线不是正式前端开发，而是：

- 打磨 Python 能力内核
- 设计接口边界
- 沉淀任务结构

只有当后端接口稳定后，正式前端接入才有意义。

### 8.4 推荐做法

推荐保留双前端结构：

- `Streamlit`：内部调试台 / 算法验证台 / 运维辅助台
- `React`：正式面向用户的产品前端

这样你不会浪费现在已经做好的原型价值。


## 9. 数据库与存储演进路线

### 9.1 当前阶段

当前继续使用：

- `SQLite`

是合理的，因为当前重点是：

- 验证字段结构
- 验证任务结果结构
- 跑通分析链路

### 9.2 何时切换 PostgreSQL

当项目出现这些情况时，建议切 PostgreSQL：

- 开始做 FastAPI 接口层
- 开始做任务中心
- 开始做多表关系管理
- 开始做结果追踪和实验记录
- 开始考虑多用户或多项目

### 9.3 为什么推荐 PostgreSQL

对于这个项目，PostgreSQL 比 MySQL 更适合的原因在于：

- 对 JSON/半结构化数据支持更好
- 复杂查询更灵活
- 元数据和任务记录建模更舒服
- 适合存字段字典、任务参数、诊断结果、报告索引等内容

### 9.4 MySQL 能不能用

可以用。

如果你短期对 MySQL 更熟，也不是不能做。

但从长期产品化角度，PostgreSQL 更推荐。

### 9.5 对象存储什么时候上

对象存储主要用于保存这些内容：

- 原始上传文件
- 导出的 CSV/Excel
- EDA 报告
- 模型文件
- 可视化导出图
- 日志归档

推荐后期使用：

- `MinIO`

但在当前阶段完全可以先用本地目录存储。

推荐演进方式：

- 阶段 A/B：本地磁盘目录
- 阶段 C/D：MinIO 或云对象存储


## 10. 部署演进路线

### 10.1 当前阶段

当前部署形态：

- 本地运行
- Conda 环境
- Streamlit 启动

是合理的。

### 10.2 中期部署

当开始引入 FastAPI 和异步任务时，建议进入 Docker 化阶段：

- API 服务容器
- Worker 容器
- Redis 容器
- PostgreSQL 容器

### 10.3 Nginx 的角色

Nginx 不是分析逻辑的一部分，它是流量入口层。

主要负责：

- 统一访问入口
- 反向代理
- HTTPS
- 静态前端资源分发
- API 转发

### 10.4 你现在是否需要学 Nginx

不需要现在就深学。

当前只要知道：

- 它负责“把外部请求转发给前端和后端”

等正式部署阶段再补就可以。


## 11. 你当前最合理的技术策略

结合你现在的背景，推荐采用下面的策略：

### 11.1 当前聚焦

继续聚焦：

- `Python`
- `数据分析链路`
- `服务层抽象`
- `任务结构设计`

### 11.2 当前只理解角色，不必深学

暂时只要理解这些技术未来做什么，不用现在投入大量时间：

- React：正式前端
- TypeScript：正式前端工程化
- ECharts：正式图表层
- PostgreSQL：正式业务数据库
- MinIO：正式文件存储
- Nginx：正式部署入口

### 11.3 现在最不该做的事

当前最不建议的事情是：

- 为了“看起来像产品”而提前重写所有前端
- 在核心链路未稳定前引入过多部署组件
- 一边补算法一边重做正式架构


## 12. 推荐执行顺序

接下来建议按下面顺序推进：

### 第一步

继续把当前分析链路做厚：

- 预处理
- EDA
- 统计检验
- 统计诊断
- 建模输入结构

### 第二步

开始定义接口边界：

- 哪些功能是同步接口
- 哪些功能是异步任务
- 输入输出 JSON 结构是什么

### 第三步

建立任务中心模型：

- `task_id`
- `status`
- `progress`
- `result_location`
- `error_message`

### 第四步

引入 FastAPI，逐步把现有服务层封成 API。

### 第五步

等后端接口稳定后，再启动 React 正式前端。

### 第六步

最终再做：

- PostgreSQL
- Redis
- MinIO
- Docker
- Nginx


## 13. 下一阶段最值得做的事

如果以“最少分心、最高产出”为目标，下一阶段最值得做的是：

### 13.1 任务中心设计

把所有耗时操作抽象成统一任务结构。

### 13.2 建模模块输入输出协议

先把未来机器学习/统计建模模块的输入输出格式统一下来。

### 13.3 API 设计草稿

即便现在不马上写 FastAPI，也可以先写接口草稿。


## 14. 结论

当前最优策略不是立刻重做前端，也不是立刻补齐完整部署栈。

当前最优策略是：

`继续用 Streamlit 做原型验证`

同时：

`把 Python 核心能力、服务层、任务结构和接口边界先做稳`

等这些能力稳定后，再演进到：

`React 前端 + FastAPI 后端 + PostgreSQL + 异步任务 + Docker + Nginx`

这条路线最稳，也最适合你当前的知识结构和项目阶段。
