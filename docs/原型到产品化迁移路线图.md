# 原型到产品化迁移路线图

## 1. 文档目的

这份文档用于回答一个现实问题：当前项目已经不再只是 `Python + Streamlit + SQLite` 的早期原型，而是进入了 `FastAPI + React 工作台 + SQLite` 的联调阶段。接下来如何在不打断主线开发的前提下，逐步演进到正式产品形态。

目标不是一次性引入所有新技术，而是按阶段把能力做稳、接口做清、前后端做分层、部署做标准化。

## 2. 当前所处阶段

当前更准确的定位是：

`产品原型验证阶段的中后段`

已经具备的能力：

- 原始数据上传与落库
- 预处理数据版本落库
- 字段类型自动识别
- 字段人工标注与字典修订持久化
- EDA、统计检验、统计诊断
- 经典统计建模与轻量机器学习建模
- 任务中心、日志、运行监控
- React 工作台与 FastAPI 真实接口联调

当前技术形态：

- 内核：Python
- API：FastAPI
- 原型前端：Streamlit
- 产品前端方向：React + TypeScript
- 存储：SQLite

这意味着项目已经完成了“只有算法逻辑”的阶段，正在进入“接口化 + 产品化前端”的过渡区间。

## 3. 总体迁移原则

### 3.1 先稳主链路，再扩技术栈

真正决定这个产品可不可用的，不是先上多少基础设施，而是以下链路是否稳定：

- 数据接入
- 字段理解与人工纠偏
- 预处理执行
- 统计诊断
- 建模执行
- 结果记录与可追溯

### 3.2 先接口稳定，再做正式前端深化

React 前端已经启动，但当前阶段的重点不是把所有页面一次性做满，而是保证：

- 接口输入输出结构稳定
- 错误信息清晰
- 任务状态一致
- 字典、日志、结果可以追踪

只有 API 边界清楚，后续正式前端重构成本才低。

### 3.3 先单机跑通，再升级为异步和多服务

当前用本地单机开发完全合理。等预处理、建模、导出等耗时任务稳定后，再引入：

- 异步任务队列
- 独立 worker
- PostgreSQL
- 对象存储
- Nginx / Docker 部署

### 3.4 学习成本服务于进度

你当前最熟的是 Python，这并不会阻碍项目推进。前端和部署相关技术不需要一次性学完，只需要按迁移阶段理解它们分别解决什么问题：

- React / TypeScript：正式产品前端
- PostgreSQL：更强的业务数据存储
- MinIO：文件与产物存储
- Docker：标准化部署
- Nginx：统一入口与反向代理

## 4. 推荐阶段划分

## 5. 阶段 A：把分析内核做稳

### 目标

继续完善数据科学主链路，让数据进入系统后，可以稳定完成从预处理到诊断再到建模的闭环。

### 重点任务

- 细化预处理策略到字段级
- 完善单位、范围、比例、量纲等元数据约束
- 扩展统计检验与统计诊断结果解释
- 完善建模任务输出结构
- 统一产物、日志、报告结构

### 这一阶段暂时不必重点投入

- 鉴权系统
- 多租户
- 微服务拆分
- 正式部署编排

### 产出标准

- 同一份数据可重复运行得到一致结果
- 每次任务都有可追踪记录
- 每个字段的关键元数据可保存与回看
- React 和 Streamlit 都能消费同一套服务层

## 6. 阶段 B：把 API 体系做完整

### 目标

让前后端彻底围绕 FastAPI 接口协同，减少界面层对底层实现细节的直接依赖。

### 当前已完成的部分

- 数据集上传接口
- 数据集预览接口
- 字段字典读写接口
- 预处理任务接口
- 建模任务接口
- 任务中心与监控接口

### 这一阶段还要继续做的事

- 统一错误码和错误消息
- 将更多统计分析能力接口化
- 梳理统一的请求模型与响应模型
- 增加结果导出接口
- 为后续异步任务预留 `task_id` 工作模式

## 7. 阶段 C：把同步执行升级为异步任务

### 为什么需要异步

当系统开始处理以下任务时，同步接口体验会明显下降：

- 较大文件上传与解析
- 长耗时预处理
- 批量统计检验
- EDA 报告生成
- 模型训练
- 超参数搜索
- 报告导出

### 建议方案

- 任务队列：`Celery` 或 `RQ`
- 中间件：`Redis`
- 工作模式：前端提交任务，后端立即返回 `task_id`，前端轮询状态接口

### 先异步化哪些模块

- 预处理任务
- 建模任务
- 报告导出

## 8. 阶段 D：正式前端产品化

### 当前判断

现在已经可以继续沿 React 主线推进，不需要回到“只有 Streamlit”的形态。

### 推荐前端定位

- `Streamlit`：内部调试台、算法验证台、快速原型页
- `React`：正式用户工作台、任务中心、监控页、看板页

### React 前端后续重点

- 页面拆分更细
- 增加统一状态管理
- 完善表单校验和错误提示
- 对接更多分析模块接口
- 后续再考虑鉴权和角色体系

## 9. 存储演进路线

### 当前阶段

继续使用 `SQLite` 是合理的，因为现在重点是：

- 验证表结构
- 验证任务链路
- 验证接口设计

### 什么时候迁移 PostgreSQL

出现以下任一情况时，应进入迁移排期：

- 接口和任务明显增多
- 需要更稳定的并发读写
- 需要更复杂的查询
- 需要更清晰的任务、版本、实验关联关系
- 需要部署到多环境

### 为什么更推荐 PostgreSQL

- 更适合复杂业务查询
- 对 JSON/半结构化字段更友好
- 更适合任务记录、字典元数据、实验记录等场景

## 10. 文件与产物存储演进

### 当前阶段

仍可先使用本地目录保存：

- 上传文件
- 导出数据
- 报告
- 模型产物

### 后续方向

进入产品化部署后，引入：

- `MinIO` 或云对象存储

它主要用于：

- 原始上传文件归档
- 报告文件
- 模型文件
- 图表导出
- 日志归档

## 11. 部署演进路线

### 当前

- 本地 Conda 环境
- 本地 FastAPI
- 本地 React 开发服务器

### 中期

建议迁移到 Docker 组合部署：

- API 容器
- Worker 容器
- Redis 容器
- PostgreSQL 容器
- 前端静态资源容器

### 正式阶段

通过 Nginx 提供：

- 统一入口
- 反向代理
- HTTPS
- 静态资源分发
- API 转发

## 12. 一句话结论

当前不需要转向 Java 前端架构，也不需要暂停主线去先学完整前端体系。最合理的路径是：继续用 Python 把分析内核和 FastAPI 做稳，同时让 React 工作台逐步接入更多真实接口；等任务和数据结构稳定后，再把存储升级到 PostgreSQL，把执行升级为异步任务，把部署升级到 Docker + Nginx。
